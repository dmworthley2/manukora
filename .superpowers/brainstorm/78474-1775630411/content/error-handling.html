Error Handling & Failure Modes

What happens when an agent fails, times out, or produces nothing

⚡ Analyst fails to submit sections
Orchestrator checks briefing_section count after analyst-agent returns. If 0 sections: mark blackboard overall_status: "failed", is_final: true. Frontend shows error state. No auditor invoked.
⚡ Auditor fails to review
Orchestrator checks for any auditor activity after auditor-agent returns. If none: auto-approve all sections (auditor_status: "approved", is_approved: true). Briefing finalizes without challenges. Degraded but functional.
⚡ Agent exceeds 2-pass cap
Loop exits after iteration 2 regardless of stop_reason. Whatever the agent has written to the DB at that point is used. Orchestrator logs a warning: "Agent capped at max iterations."
⚡ Anthropic API error mid-loop
Agent function catches the error and returns whatever it has committed to the DB. Orchestrator treats partial output as valid and continues. If nothing was committed: orchestrator marks blackboard failed.
⚡ Edge function timeout
Supabase edge functions have a 150s wall-clock limit. Orchestrator invokes agents via supabase.functions.invoke() sequentially — each agent has ~40s budget. If a function times out, the orchestrator catches the error and proceeds with partial data.
✓ Always-final guarantee
Orchestrator wraps the full pipeline in try/finally. The finally block always sets is_final: true — even on total failure. Frontend never polls forever. The status field tells the UI what to show.
