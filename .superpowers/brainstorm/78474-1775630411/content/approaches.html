Three Agent Architecture Approaches

How should the analyst and auditor be structured as goal-oriented agents?

A

Orchestrator + Tool-Loop Agents Recommended

A lightweight briefing-orchestrator coordinates three separate edge functions. analyst-agent and auditor-agent each run a real tool-use loop — they decide which tools to call (query inventory, query sales, read sections, read past challenges), reason over results, and decide when they're done. Loop caps at 2 iterations.

Pros

  • True agentic behaviour
  • 2-pass cap maps cleanly to loop limit
  • Each agent is independently testable
  • Orchestrator is simple and auditable

Cons

  • 3 edge functions to deploy
  • More moving parts
B

Event-Driven Autonomous Agents

No orchestrator. Each agent is triggered by DB state changes via Supabase webhooks. Analyst fires on new blackboard → writes sections → sets status. Auditor fires on status change → queries data, challenges → sets status. Analyst fires again on "challenged". Agents are fully decoupled.

Pros

  • Most autonomous design
  • No coordination code
  • Naturally parallelisable

Cons

  • 2-pass cap is hard to enforce reliably
  • Debugging event chains is painful
  • Race conditions possible
C

Single Function, Multi-Turn Conversations

Keep one edge function but give each agent a persistent multi-turn conversation history. The orchestrator maintains conversation state and feeds prior reasoning back to the model. Agents can "remember" what they said and refine — without separate deployments.

Pros

  • Least infrastructure change
  • Conversation history gives context

Cons

  • Agents not truly separated
  • Context window grows with iterations
  • Doesn't deliver the separation you asked for
