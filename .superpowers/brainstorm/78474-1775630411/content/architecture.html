Agent Architecture — Option A

Three edge functions. Two true agents. One orchestrator.

── FRONTEND ──────────────────────────────────────────
POST /api/briefings/generate
↓ calls
── EDGE FUNCTION: briefing-orchestrator ─────────────
1. Create blackboard (DB)
2. Invoke analyst-agent (mode: draft)
↓ waits for completion
3. Invoke auditor-agent
↓ waits for completion
4. Invoke analyst-agent (mode: respond)
↓ waits for completion
5. Finalize blackboard → is_final = true

── EDGE FUNCTION: analyst-agent ─────────────────────
Tool-use loop (max 2 passes)
Tools available:
• query_inventory() → agent_reasoning_feed
• query_sales() → sales_history
• read_my_sections() → own submitted sections
• read_past_challenges() → auditor history across runs
• submit_section(id, content) → briefing_section
• submit_response(id, ...) → briefing_section (respond mode)

── EDGE FUNCTION: auditor-agent ─────────────────────
Tool-use loop (max 2 passes)
Tools available:
• query_inventory() → agent_reasoning_feed
• query_sales() → sales_history
• read_analyst_sections() → briefing_section
• submit_challenge(id, ...) → briefing_section
• approve_section(id) → briefing_section

── DATABASE (shared blackboard) ──────────────────────
briefing_blackboard ← orchestrator reads/writes status
briefing_section ← agents read/write content
briefing_audit_trail ← past challenges (analyst reads)

The DB is the shared blackboard — agents communicate by writing to it, not by calling each other directly. The orchestrator reads DB state between each agent invocation.
